# ADR-005 mcp-bridge 定位为纯转发网关

- 状态：已接受（随 04 架构基线确认；自 OQ-004 结论转正）
- 驱动因素：FR-001、NFR-005、OQ-004、UC-009

## 背景

MCP 客户端（stdio）需要访问应用（HTTP，回环 + 令牌）。Plugin 分发连接器，
应用独立安装升级。连接器应该承担多少职责、持有多少信息。

## 候选方案

- **纯转发网关**（stdio↔HTTP，仅做发现、拉起与透传）；
- 智能客户端（理解业务、缓存数据、组合调用）：业务逻辑外泄、两处维护
  契约；
- 无连接器（Plugin 配置直连 HTTP + 令牌写在配置里）：令牌随项目文件
  分发，违反"凭据不随 Plugin 分发"的安全原则，且固定端口可被本机任意
  进程探测。

## 决策

mcp-bridge 是独立轻量可执行文件（`mcp-bridge/`，随 Plugin 分发），只做
三件事：读 `~/.relayharbor/runtime/bridge.json` 获取端口与令牌；应用
不可达时拉起应用并等待就绪；在 MCP stdio 与应用本地 HTTP API（ADR-004）
之间双向透传。不含业务逻辑、不缓存业务数据、不持有用户凭据。

## 主要理由

- 引导信息只经 bridge.json 一处（随机端口 + 每会话轮换令牌 + 用户级
  文件权限），无凭据分发面（NFR-005）；
- 连接器永不区分本地/远程项目：远程也经本地应用转发（OQ-004），此定位
  使该规则天然成立；
- 工具契约演进只改应用一侧，Plugin 只需保持传输兼容。

## 代价与后果

- Agent 的写入依赖应用存活：由 bridge 拉起能力缓解（UC-009 A1），代价
  已在 00 概览风险中记录；
- 多一层进程与一次转发延迟（本地回环，可忽略）。

## 验证或重新评估条件

- 令牌轮换后旧令牌失效、bridge 重发现成功的测试（UC-009 A2）；
- 重新评估触发：MCP 生态提供标准本地发现机制时（可替换 bridge.json
  引导而不改定位）。
