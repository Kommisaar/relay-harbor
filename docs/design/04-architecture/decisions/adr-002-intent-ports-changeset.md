# ADR-002 存储端口意图级化，以 ChangeSet 为唯一原子单位

- 状态：已接受（随 04 架构基线确认）
- 驱动因素：NFR-009、NFR-001、BR-005、DOM-005、CON-002

## 背景

领域需要"多条相关修改单事务提交 + 乐观并发 + 修订审计"。问题是：事务
边界暴露到哪一层。M1 全部写入来自 MCP 工具（变更集原子提交是所有写入
用例的公共路径，见业务过程二）。

## 候选方案

- **意图级原子端口**：Storage trait 只暴露表达业务意图的原子操作
  （`apply_change_set`、`transition_item` 等），事务、OCC、审计全部封闭
  在单个 SQL 事务内，由 infra 实现；
- 通用 UoW / Repository + 事务对象跨层传递：灵活，但事务泄漏成接口概念，
  调用方可以拼出半业务半技术的写法，规则保证点分散；
- 无封装（每语句自动提交）：最简单，直接违反 NFR-009。

## 决策

采用意图级端口。端口方法即业务操作；需要新的复合写入时，为端口新增
具名方法（其内部仍是单事务），不开通用事务逃生舱。ChangeSet（DOM-005）
是端口上的统一提交单位：期望修订号校验、白名单校验、环检测在
services/domain 完成后，由 `apply_change_set` 单事务落库。

## 主要理由

- "要么全部生效要么明确失败"由一个方法签名直接表达，Agent 生成的代码
  没有制造半写状态的机会；
- 事务实现细节（BEGIN IMMEDIATE、busy_timeout）不污染 domain；
- 端口方法即可测试的不变量单元（`src-tauri/tests/` 的状态机与不变式
  测试以此为锚）。

## 代价与后果

- 每种复合操作都要扩端口（样板增长）；
- 极端灵活的批量操作需要领域先"意图化"才能落地——这是刻意的摩擦。

## 验证或重新评估条件

- 集成测试注入失败点验证无半写（NFR-009 验证方式）；
- 重新评估触发：若出现无法收敛为意图的合法写模式（预期是远程多用户
  时代），届时再议通用事务面。
